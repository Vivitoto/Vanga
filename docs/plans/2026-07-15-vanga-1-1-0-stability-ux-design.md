# Vanga 1.1.0 稳定性与体验大版本设计

## 背景

Vanga 当前已经具备 Komga 在线浏览、图片阅读器、EPUB 入口、Komf 设置/任务、下载与离线阅读入口、版本发布脚本等基础能力。1.0.x 版本主要做了 UI 和发布一致性修复；1.1.0 目标是把这些能力整理成一个更稳定、更清楚、更可发布的大版本。

本版本采用一次性大版本方案：`1.1.0`，Android `versionCode` 从当前 `22` 升至 `23`。

## 总目标

Vanga 1.1.0 的定位：

> 让 Vanga 成为一个更可靠的 Komga 在线漫画/图书客户端，并让“下载到本地后离线阅读”成为清晰、稳定、可恢复的一等体验。

本版本覆盖五条主线：

1. 离线下载与离线阅读稳定化
2. 阅读器手感与失败恢复优化
3. Komf 功能优化，重点补上单本书籍元数据识别/刮削
4. 书籍 / 系列列表体验优化
5. 版本发布链路硬化

## 非目标

1. 不把 Vanga 离线模式做成完整 Komga 服务端等价实现。
2. 不在离线模式下完整支持 Library / Collection / ReadList / User 管理。
3. 不在 1.1.0 中重写 EPUB 阅读器架构。
4. 不重构整个 Komf 设置架构。
5. 不做远端写操作的语义扩大；所有可能影响 Komga 服务端的行为必须维持现有权限与确认方式。

## 设计原则

- **离线 = 下载到本地阅读**：离线功能的主价值是把漫画/书籍下载到本机，断网仍可阅读。
- **不支持也要可解释**：暂不支持的离线管理操作不能 `TODO()` 崩溃，必须明确提示。
- **单本 Komf 不误伤系列**：新增单本书籍元数据识别时，必须确保只影响目标书籍，不能误触发系列级刮削。
- **小步可验证**：每条主线拆成可测试的小任务，优先补纯逻辑测试。
- **发布一致性优先**：版本号、Release Notes、README、`AppVersion.current` 和构建元数据必须一致。

## 1. 离线下载与离线阅读稳定化

### 当前状态

已有能力：

- 单本书页面存在下载入口。
- 系列页面存在整部作品下载入口。
- `BookDownloadService` 会从 Komga 下载原始 book 文件到本地，并保存 server / user / library / series / book 元数据。
- 登录页存在“离线阅读 / 进入离线模式”。
- Book 信息里已有“本地下载已过期”提示。

不足：

- 下载状态和失败原因不够清楚。
- 部分离线 API / Action 仍有 `TODO()`，误触会崩。
- 离线模式下部分在线管理功能没有明确禁用或说明。
- 本地文件缺失、权限失效、下载目录不可写等情况缺少统一提示。

### 目标体验

用户在线时可以下载单本或整部作品；离线时可以进入“离线阅读”，看到并阅读已下载内容。若内容未下载、文件丢失、文件过期或权限不可用，Vanga 应给出清楚解释与恢复建议。

### 设计

#### 1.1 下载状态模型

梳理现有 `DownloadEvent`，在 UI 层统一展示：

- 等待中 / 准备中
- 下载中：已下载字节数 / 总字节数
- 已完成
- 失败：带人话错误原因
- 已下载但本地文件过期
- 已下载但本地文件缺失 / 权限失效

若现有 domain event 不足，优先在 UI 映射层增加派生状态；只有必要时才扩展 domain model。

#### 1.2 单本下载

- 点击下载后禁用重复触发，避免同一本多次入队。
- 下载失败时显示：失败原因 + 重试入口。
- 删除已下载文件时明确提示：只删除本地文件，不删除 Komga 远端。
- 本地文件过期时提示重新下载。

#### 1.3 系列下载

- 保留整部作品下载入口。
- 展示整体进度：已完成 X / 总数 Y，当前下载书名。
- 已下载且未过期的书跳过或显示为已完成。
- 部分失败不应让整体体验崩溃；提供失败项重试入口或至少明确失败数量。

#### 1.4 离线阅读入口

- 登录页“离线阅读”文案补充：阅读已下载到本机的漫画/书籍。
- 离线模式下优先展示本地可读内容。
- 未下载内容若可见，打开时提示联网下载后再离线阅读。

#### 1.5 未支持离线管理操作

以下操作在 1.1.0 中不做完整离线等价实现，只做安全兜底：

- 离线新增 / 扫描 / 分析 / 刷新 Library
- 离线刷新 Book / Series 元数据
- 离线上传 / 选择 / 删除 Book / Series 缩略图
- 离线 Collection / ReadList 管理
- 离线用户管理
- 离线 PDF 页内容抽取
- wasm 平台离线下载

处理方式：

- 移除高风险 `TODO()`。
- 返回明确 unsupported 错误或空结果。
- UI 显示“离线模式暂不支持此操作，请连接 Komga 后再试”。

### 验收标准

- 离线下载/阅读主线不因 `TODO()` 崩溃。
- 单本下载失败有明确提示，可重试。
- 删除已下载文件明确“不删除远端”。
- 离线模式下在线管理操作不会直接崩溃。
- 至少补覆盖 unsupported 行为和下载状态映射的单元测试。

## 2. 阅读器手感与失败恢复优化

### 当前状态

Vanga 图片阅读器支持分页 / 连续阅读、阅读方向、缩放、拉伸适配、裁边和采样设置。近期已修复跨页面导航返回列表滚动位置丢失问题。

### 目标体验

阅读过程中减少卡顿、迷路和失败后的无助感；异常图片、大图或本地文件问题应有可理解提示和恢复动作。

### 设计

#### 2.1 图片加载失败恢复

- 阅读器中图片加载失败时展示更明确错误状态。
- 提供“重试加载”入口。
- 若在离线模式且本地文件缺失，提示重新联网下载。

#### 2.2 翻页/滚动状态恢复

- 为分页阅读和连续阅读补回归测试，确保退出再进入、切后台返回、设置变化后位置恢复稳定。
- 对异常边界页码进行 clamp，避免越界状态传播。

#### 2.3 大图/双页边界保护

- 双页模式遇到极端宽高图时不应抛异常。
- 对“无法显示超过 2 张图”等内部异常做保护或更清楚错误。

#### 2.4 阅读帮助与交互提示

- 阅读器帮助文案补充关键手势/按键。
- 在适合的位置提示当前阅读模式和可用操作。

### 验收标准

- 图片加载失败不白屏、不静默。
- 阅读状态恢复有测试覆盖。
- 边界页码/异常布局不导致崩溃。

## 3. Komf 功能优化与单本书籍元数据识别

### 当前状态

现有 Komf 识别主要围绕系列：

- `searchSeries`
- `identifySeries`
- `matchSeries`
- `matchLibrary`
- 系列/书库菜单有 Komf 自动识别入口。

单本书菜单目前只有普通“刷新元数据”，没有明确的 Komf 单本识别入口。现有 `snd.komf.client.KomfMetadataClient` 1.6.1 暴露的公开封装也以系列/书库为主。任务事件中有 `ProviderBookEvent`，说明任务进度层面可以表达单本数据处理，但启动任务的 book-level API 需要进一步确认。

### 目标体验

Komf 不只可刮削系列元数据，也能对单本书籍触发元数据识别；如果服务端或当前 Komf 版本不支持单本识别，Vanga 必须明确提示，而不是误触发系列刮削。

### 设计

#### 3.1 接口确认与兼容 client

实现前必须确认 Komf 服务端是否提供 book-level metadata identify/search/match endpoint。

策略：

1. 优先使用 `snd.komf.client` 已有 book-level API，如果存在。
2. 如果 client 未封装但服务端有 endpoint，则在 Vanga 内部新增最小兼容 wrapper。
3. 如果服务端不支持 book-level identify，则 UI 显示“当前 Komf 版本不支持单本元数据识别”。

不得把单本识别伪装成系列识别。

#### 3.2 单本入口

新增入口：

- Book 页面菜单：`自动识别单本元数据（Komf）`
- Oneshot 页面菜单：同样支持单本识别

入口显示条件：

- Komf 已启用
- 当前不在离线模式
- 当前书籍有 `libraryId` / `seriesId` / `bookId` 上下文

#### 3.3 单本识别弹窗

新增或泛化现有 `KomfIdentifyDialog`：

- Series 模式：保持现有行为。
- Book 模式：默认搜索词为书籍标题。
- Book 模式确认后调用 book-level identify/match，目标只包含当前 `bookId`。

如果 Komf book-level 搜索结果模型和 series result 不同，需要新增 `KomfBookResultCard` 或泛化 card model。

#### 3.4 任务进度与错误处理

- 复用现有 job event 进度 UI。
- `ProviderBookEvent` 显示“正在获取单本数据”。
- API 失败时显示人话错误，并允许复制错误信息。
- 若 endpoint 404 / unsupported，提示当前 Komf 版本不支持单本识别。

### 验收标准

- 系列 Komf 识别仍可用。
- 书库 Komf 自动识别仍可用。
- 单本书籍有独立 Komf 识别入口。
- 单本识别不会误刮整个系列。
- 不支持 book-level API 时有明确提示，不崩溃。

## 4. 书籍 / 系列列表体验优化

### 当前状态

1.0.12 已修复跨页面导航返回系列列表时滚动位置丢失问题。系列详情和书籍列表已有视图切换、阅读状态、下载状态等数据基础。

### 目标体验

书多、系列多时更容易定位、筛选和继续阅读。

### 设计

#### 4.1 系列详情书籍搜索

- 在系列详情书籍区域增加搜索入口。
- 支持按书名/编号过滤。
- 搜索状态不破坏现有视图模式和滚动恢复。

#### 4.2 阅读状态筛选

支持筛选：

- 全部
- 未读
- 阅读中
- 已读

#### 4.3 下载状态筛选

支持筛选：

- 全部
- 已下载
- 未下载
- 本地文件过期

#### 4.4 收藏筛选与排序入口

- 若现有数据模型有收藏状态，则提供收藏筛选。
- 排序入口更明确：标题、编号、更新时间、阅读进度等，以现有 API / repository 支持为准。

### 验收标准

- 系列详情中可快速搜索书籍。
- 筛选不会破坏阅读按钮、下载按钮和批量操作。
- 返回页面后滚动位置仍保持。
- 补充纯逻辑测试，覆盖过滤/排序状态。

## 5. 版本发布链路硬化

### 当前状态

Vanga 已有：

- `scripts/verify_app_version.py`
- GitHub Actions 构建/发布 APK
- API 推送脚本本地已新增但尚未推远端

此前出现过版本号 / Release body 不一致，以及本机 `git push` / `git fetch` 443 超时问题。

### 目标体验

发布前能自动发现版本不一致和高风险状态；推送默认走 GitHub API；发布后用 API / Actions / Release 校验，不依赖普通 git 网络。

### 设计

#### 5.1 API 推送流程纳入 1.1.0

保留并发布：

- `scripts/push-via-api.py`
- `docs/github-api-push.md`

推送前仍必须经用户确认。

#### 5.2 加强版本校验

`scripts/verify_app_version.py` 检查：

- `gradle/libs.versions.toml` app version
- Android versionCode
- `AppVersion.current`
- README 当前版本
- RELEASE_NOTES 顶部版本
- Release Notes 中 versionCode

#### 5.3 doctor 脚本

新增或扩展发布前检查脚本，例如 `scripts/doctor.py`：

- 运行版本一致性检查
- 检查高风险 `TODO()` 列表
- 检查 API push 脚本语法和 dry-run
- 检查 GitHub Actions workflow 是否存在
- 输出明确 pass/fail

#### 5.4 1.1.0 版本 bump

最终功能完成并验证后再 bump：

- `1.0.12` -> `1.1.0`
- `versionCode = 22` -> `23`
- README / RELEASE_NOTES 同步

### 验收标准

- `python3 scripts/verify_app_version.py` 通过。
- doctor 脚本能在本机缺 JDK 时给出明确跳过/阻塞原因。
- 版本元数据全一致。
- API 推送流程文档和脚本进入仓库。

## 测试策略

本机当前没有可用 Java/JDK，因此本地 Gradle 测试可能被环境阻塞。策略：

1. 优先补纯 Kotlin/common 逻辑测试。
2. 本地可运行的 Python 脚本和静态检查必须跑：
   - `python3 scripts/verify_app_version.py`
   - `python3 -m py_compile scripts/*.py`
   - `git diff --check`
3. 若本机无 Java，明确记录 Gradle 测试无法运行；推送后以 GitHub Actions 作为完整构建验证。
4. 每个阶段尽量小 commit，失败可回滚。

## 风险与缓解

### 风险：范围过大

缓解：虽然作为一个 1.1.0 大版本交付，但实现时按主线分 commit；每条主线有独立验收。

### 风险：Komf 单本识别 API 不存在

缓解：先做接口探测/兼容 wrapper；不存在时显示明确 unsupported，不伪装成系列识别。

### 风险：离线模式误做成完整 Komga 管理

缓解：明确非目标；1.1.0 只让下载到本地阅读稳定可靠，管理操作只做安全兜底。

### 风险：发布流程误触发

缓解：所有推送/发布前仍按全局规则列清单确认；默认用 `scripts/push-via-api.py`。

## 初步实施顺序

1. 发布链路基础：API push 脚本/文档纳入计划，确认当前本地状态。
2. 离线 unsupported 错误模型和 TODO 兜底。
3. 离线下载状态与 UI 文案强化。
4. 阅读器失败恢复和状态回归测试。
5. Komf 单本识别接口探测与兼容 wrapper。
6. Komf 单本 UI 入口与弹窗。
7. 列表搜索/筛选/排序。
8. 版本 bump 到 1.1.0，更新 Release Notes，跑发布前检查。

## 已确认的设计点

1. 离线模式按 A 方案：只完善“下载到本地离线阅读”，不做完整离线 Komga 管理。
2. 离线模式下不支持的管理操作不保留无意义入口：UI 中直接隐藏/去掉；底层仍保留 unsupported 兜底，防止旧路径或误调用崩溃。
3. Komf 单本识别：若当前 Komf 服务端版本不支持，Vanga 显示明确提示，不做假识别。
4. 1.1.0 一次性发布，但内部按主线分 commit。
